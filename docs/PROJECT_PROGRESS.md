## 1. Project overview

Snipe-Proof Meme Launch is being developed as a fairer meme-token launch
mechanism. The current technical direction is:

1.  Collect bids from participants.
2.  Keep bid information private until the auction is cleared (the
    intended sealed-bid flow).
3.  Run deterministic auction-clearing logic in a WebAssembly workload.
4.  Use OutLayer's execution environment and, once verified, its
    attestation mechanism to provide evidence about execution.
5.  Return allocations and clearing-price information to the
    application/backend.
6.  Integrate the verified result into the broader launch and settlement
    workflow.

**Important scope distinction:** The Rust auction-clearing program
exists and has been tested locally. The broader sealed-bid workflow, bid
confidentiality, on-chain settlement, token distribution, and production
verification are not complete merely because the Rust program or
OutLayer project exists.

## 3. Rust auction engine

### 3.1 Implementation

The original engine is in `outlayer-auction/src/main.rs`.

It accepts JSON with this shape:

``` json
{
  "action": "clear_auction",
  "supply": 100,
  "reserve_price": 10,
  "bids": [
    {"bidder": "alice", "quantity": 60, "limit_price": 20},
    {"bidder": "bob", "quantity": 80, "limit_price": 15},
    {"bidder": "charlie", "quantity": 50, "limit_price": 15}
  ]
}
```

The program uses `serde` and `serde_json` to parse and serialize JSON.

### 3.2 Current auction rules implemented

The prototype currently:

-   Requires supply to be greater than zero.
-   Rejects empty bidder identifiers.
-   Rejects zero bid quantities and zero limit prices.
-   Rejects duplicate bidder identifiers (one bid per bidder in this
    prototype).
-   Sorts bids by descending limit price, with bidder identifier as a
    deterministic secondary sort.
-   Ignores bids below the reserve price.
-   Fills higher-price tiers before lower-price tiers.
-   If a price tier is oversubscribed, allocates the remaining supply
    pro rata.
-   Uses largest remainders to distribute indivisible units, with bidder
    identifier as the deterministic tie-breaker.
-   Uses the reserve price when eligible demand does not exhaust supply.
-   Uses the oversubscribed marginal tier's price when supply is
    exhausted in that tier.
-   Sets the same final clearing price for every allocation.
-   Sorts final allocations by bidder identifier.
-   Uses checked arithmetic for demand/allocation totals and returns
    JSON errors for invalid requests.

These are the current prototype rules, not a claim that every economic
or legal detail of a production auction has been finalized. The auction
policy should be reviewed and formally specified before handling real
funds.

### 5.4 OutLayer execution attempts

A direct WASM execution was attempted using the CLI's `--wasm` option.
Project-based execution was also attempted using the JSON input file.

The JSON file initially had a UTF-8 BOM (`EF BB BF`), which caused the
CLI to report invalid JSON. The BOM was removed using:

``` powershell
$content = Get-Content .\auction-input.json -Raw
$content = $content.TrimStart([char]0xFEFF)

[System.IO.File]::WriteAllText(
    (Resolve-Path .\auction-input.json),
    $content,
    [System.Text.UTF8Encoding]::new($false)
)
```

After this, the CLI accepted the input and submitted execution requests.

One execution transaction examined in NEARBlocks was:


a successful `on_execution_response` callback. However, the callback
payload contained this execution outcome:

``` json
  "standard": "near-outlayer",
  "version": "1.0.0",
  "event": "execution_completed",
  "data": [
    {
      "success": false,
      "error_message": "wasm_url could not be fetched",
      "compilation_note": "Compilation failed",
      "resources_used": {
        "instructions": 0,
```

**Interpretation:** The NEAR transaction and callback can succeed while

## 9. Backend integration plan after OutLayer is working

The intended application flow is:

``` text
Next.js frontend
      |
      v
Fastify backend
      |
      | Validate bids / construct auction input
      v
OutLayer execution interface
      |
      | WASM execution + response + attestation
      v
Fastify backend
      |
      | Validate response and attestation
      v
Auction result / application state
```

Before production integration, the backend should:

-   Validate all bid fields and bidder identity.
-   Enforce the one-bid-per-bidder policy if that remains the auction
    rule.
-   Prevent replay or duplicate auction clearing.
-   Bind the auction input to a specific auction ID and configuration.
-   Persist the exact input, WASM version/hash, execution identifier,
    result, and attestation reference.
-   Verify the attestation using the platform's official verification
    process.
-   Reject results if the code hash, input, auction ID, or attestation
    does not match.
-   Handle retries idempotently.
-   Keep payment and settlement logic separate from the auction
    calculation.
-   Avoid treating a successful NEAR transaction as proof that the WASM
    execution succeeded.

The current backend has previously used a mock payment provider. Do not
present mock payment behavior as live NEAR token settlement.

## 10. Auction-engine work still worth doing locally

While waiting for OutLayer support, useful development work can continue
without spending testnet funds:

1.  Add automated unit tests for the auction rules.
2.  Test empty bids, all bids below reserve, exact supply,
    oversubscription, equal remainders, duplicate bidders, zero
    quantity, zero price, and integer-overflow boundaries.
3.  Add property-based tests for invariants:
    -   Total allocation never exceeds supply.
    -   No allocation exceeds the requested quantity.
    -   No ineligible bid receives allocation.
    -   All allocations share one clearing price.
    -   Output is deterministic for identical input.
4.  Define the auction's economic policy precisely, including the
    reserve-price rule and marginal-price behavior.
5.  Review whether bidder identifiers are suitable tie-breakers or
    whether a committed deterministic random tie-break is required.
6.  Add a versioned input/output schema.
7.  Add integration tests around the backend interface using a local
    Wasmtime process or mock execution adapter.
8.  Document the threat model: what is private, who can observe inputs,
    when bids are revealed, and what the attestation actually proves.
